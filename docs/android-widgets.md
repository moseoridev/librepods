# Android controls widget

The AirPods controls widget shows listening modes and AirPods battery status. Each instance routes to a configured device. The layout follows the Buds 4 Manager 9.0.00.1604 renderer. See [migration state](rewrite-migration.md) for the rewrite port.

## State and publication

Implementation lives under `android/app/src/main/kotlin/me/kavishdevar/librepods/presentation/widgets/`. `WidgetState` normalizes component batteries and confirmed noise mode; `WidgetPublisher` constructs complete RemoteViews containing both state and click actions. `NoiseControlWidget` and `WidgetSettingsActivity` share that path. `WidgetDataSource` reads the configured device from `WidgetConfigRepository`, live state from `CompanionConnection.activeEngine` and offline metadata from `AppleRepository`. Appearance remains in the existing per-instance controls preferences. Each command PendingIntent identifies its widget; another widget cannot overwrite its target. Connection ownership and optional BLE snapshots are described in [lifecycle notes](android-background-lifecycle.md).

- A new AACP session waits for an accepted battery packet. Rejected packet lengths cannot make cached data fresh or trigger popup/audio decisions. Noise mode stays unselected until confirmed.
- Disconnection clears mode selection, disables commands and displays a regular-weight localized status when there are no readable levels. The header opens the app. The battery display omits unknown component readings and keeps valid 0% readings. When connected with no displayable readings, the battery area is empty and the widget exposes an accessibility description.
- Connection, battery, mode/allowed-mode and relevant setting changes drive publication. The cache includes content, settings, geometry and appearance. New instances, system updates and resize force a complete publication. Missing widgets return early; bitmap caches are bounded.

Widget state updates and direct mode commands start no scanner, polling, wake lock or engine binding. Header/battery clicks open MainActivity, whose normal UI lifecycle binds the engine and reconciles connection/Nearby settings. Optional Nearby data can expire while the process is frozen; a previously published widget may then persist until its next update.

## Layout and appearance

The App Appearance setting sets the platform per-app night configuration used by the widget configuration activity and its preview. Launcher RemoteViews resolve day/night colors in the host configuration. An instance set to Match phone settings can therefore differ from the in-app preview when the app uses a different theme from the system. See the [appearance verification notes](/Users/moseoridev/programming/android/librepods/evidence/compose-residuals-cold-20261113/app-night-mode-20261115/README.md).

The widget supports 2×1, 4×1, 2×2 and 4×2 layouts. Exact host sizes select geometry. Hosts without size lists get portrait and landscape alternatives from min/max bounds. Enlarged configuration previews preserve the original layout type and scale seams and metrics together. Configuration uses explicit Save and Cancel, and widget restore snapshots the old IDs' settings before applying them to the new IDs.

Narrow layouts use one mode-cycle button. Wide layouts use linked mode buttons, with Off omitted when unavailable. Compact layouts show earbud battery. Taller layouts add the device title and case battery. Tall layouts measure a wrap-content header with natural font padding, then distribute remaining space through weighted containers. Wide tall layouts also distribute the remaining row width between buttons using Android measurement and rounding. Equal valid earbud levels and charging states combine into one display. Charging uses an inset bolt in a leading slot. When a compact layout shows separate earbud rows and either earbud is charging, both labels align after the slot.

The inspected Buds 4 Manager 9.0.00.1604 home-content path informs geometry and layout behavior. Packaged mode icons now reuse the upstream LibrePods `noise_cancellation`, `transparency` and `adaptive` resources, including the existing Off mapping. Charging uses the upstream `ic_power` path in an inset viewport. Widget-only inset drawables reserve 15% on each edge around the upstream mode artwork. Runtime rasterization and static previews share these wrappers. Runtime rasterization applies mode-glyph opacity before launcher scaling. The wrappers size the artwork within the existing touch targets. The battery separator uses a small, locally generated bitmap with its translucent fill applied before scaling. The charging vector variants put the palette color in the fill so the launcher can draw untinted edges. `sec` requests the system font by name. Sequential control/battery placement, bounded icon rasterization, natural font padding, logical RTL padding/end masks and the native link seam matter to alignment. Joined masks avoid doubled alpha at intersections. Final button colors are rasterized into cached bitmaps; the first link rectangle uses `DST_OVER`, matching the original. Post-raster tinting is cleared on reapplication because it changes premultiplied edge values. Day/night Icons let the host select appearance without waking the app. Configuration previews preserve these proportions.

Each instance offers background visibility, Match phone settings, Light and Dark color choices, and 50%, 75% or 100% background opacity. The 2×2 layout also offers corner shapes. The surface applies alpha once and the launcher can resolve its day/night colors without waking the app.

## One UI surface ownership

`WidgetSurface` follows the inspected BZI6 launcher contract. On API 37+ in the system user profile, home hosts supplying `semHostType=1` and supported `semWidgetSize` values own the final outline. The transparent outer GradientDrawable supplies the host-default sentinel or original 32/12dp custom corners, while the inner ColorDrawable supplies color/alpha. Local clipping is disabled only for that path; complete publication explicitly restores it for fallbacks. The cache includes ownership.

All non-system profiles conservatively keep local clipping because the launcher skips its outline for Knox/dual-app providers. Other hosts retain the previous mask. The finite settings preview uses the original smooth-corner curve locally and scales it with the preview; static selector artwork remains a fallback.

Samsung metadata and `android.R.id.background` participate in native launcher handling. The inspected host can read drawable alpha/corners without private string tags. Wallpaper blur is produced by the launcher's shared cache, not by this app. Eligibility depends on firmware, host state and settings; it is an undocumented OEM integration, not a public Android guarantee. The app adds no wallpaper capture or blur computation.

## Verification limits

Packaged artwork intentionally differs from Samsung. Layout and surface behavior follow the inspected renderer and launcher contracts; this is not a claim of pixel identity across devices, states or themes.

JVM regressions cover battery/mode normalization, rejected packet freshness and layout selection. The widget harness compares on-device RemoteViews content with Manager 9.0.00.1604 using synthetic accessory states on Galaxy S25. The comparison covers the four layouts, missing readings, disconnection, charging, and listening-mode and color variants. The private fixture captures both RemoteViews trees at the same screen coordinates. All 17 cases matched pixel for pixel with substituted artwork. With packaged artwork, pixel differences were confined to the mode icons and charging bolt. Full restored-ID behavior, actual Knox installation, RTL rendering, theme transitions and every size/state combination remain unverified. Build success does not establish Android receiver lifetime, power savings or responsiveness. Power/jank and long-term OEM behavior remain unmeasured.
